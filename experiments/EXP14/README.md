# EXP14 - App icon: four-quadrant rectangle (red / yellow / green / gray)

## Summary
Give the app its identity icon: one rectangle split into four flush quadrants - red, yellow, green, gray (traffic-light order) - shown as the window/taskbar icon and embedded in the `.exe` so Explorer shows it too.

## Hypothesis
A pure `app_icon_bgra(size)` (4 flush quadrants from `theme::{CLOSED, VENT, OPEN, MUTED}`)
can drive both a runtime `WM_SETICON` and an `.ico` embedded by a hand-rolled
`build.rs` + `windres`, giving a correct window *and* Explorer icon on this
GNU/MinGW setup - with every existing tray/e2e assertion still byte-identical.

Layout (traffic-light order):

```
+---------+---------+
|   red   | yellow  |   red    = Keep closed (CLOSED 0xf85149)
+---------+---------+   yellow = Vent         (VENT   0xd29922)
|  green  |  gray   |   green  = Open         (OPEN   0x3fb950)
+---------+---------+   gray   = unknown/loading (MUTED 0x8b949e)
```

Square canvas, no gap, colours reused from `theme.rs`.

## Methodology & blast radius
- **Method**
  1. Pure design source - `app/src/icon.rs`: `app_icon_bgra(size) -> Vec<u8>`
     (BGRA, top-down, same byte order as `tray::bgra`), 4 equal quadrants.
  2. Runtime window icon - build an `HICON` with the existing
     `CreateIconIndirect` recipe and `SendMessageW(hwnd, WM_SETICON,
     ICON_BIG|ICON_SMALL, icon)` from `main.rs` after the window opens.
  3. Embedded exe icon - build.rs writes the `.ico` (BMP-flavour, 16/32/48/256)
     and a one-line `.rc` into `$OUT_DIR`, runs `windres -O coff`, and links the
     object with `cargo:rustc-link-arg-bins`. `build.rs` `include`s the pure
     `icon_design.rs` via `#[path]`, so the embedded icon and the runtime icon
     share one design (no drift, no committed binary, no new crate).
  4. Verification - unit tests for the quadrant buffer + ICO header; e2e
     `ExtractIconExW` reads the icon out of the built `.exe` and asserts the four
     quadrant colours; e2e `WM_GETICON` proves the window icon; title-bar
     screenshot; full suite to confirm the tray counts.
  5. Harness fix - the e2e pixel scan used to screenshot the whole window rect;
     the title-bar icon's colours then polluted the analysis (green in the
     "headline band"). `capture.ps1` now crops to the **client area**
     (`GetClientRect` + `ClientToScreen`), so the tests analyse the widget only.
- **May touch**: `app/src/icon.rs` (new), `app/src/icon_design.rs` (new),
  `app/build.rs` (new), `app/src/main.rs`, `app/src/tray.rs`
  (share `hicon_from_bgra`), `app/tests/e2e_widget.rs`, `app/tests/capture.ps1`,
  `app/tests/icon.ps1` (new), `experiments/EXP14/**`, `experiments-overview.md`.
- **Off-limits**: `core/**`, the tray's verdict tinting / `icon_bgra` contract,
  `UI.md`, the data path. No new crates.

## Open questions (known unknowns)
- [x] Tray unchanged? - yes: keep the verdict-tinted square as-is; this
      experiment only adds the app / `.exe` / window icon.
- [x] `.ico` sourcing - resolved: generated by `build.rs` from the shared pure
      `icon_design.rs` (no committed binary, no generator example).
- [x] Build mechanism - resolved: hand-rolled `build.rs` calling `windres` on
      PATH, no new crate.
- [x] `.ico` pixel format - resolved: BMP-flavour (pure `std` encoder in

## Conclusion (findings)
Hypothesis **upheld**, with one assumption change. A single pure design
(`icon_design::app_icon_bgra`) drives both surfaces: `main.rs` builds an `HICON`
and installs it with `WM_SETICON` (big + small), and `build.rs` encodes the same
pixels into a `.ico` that `windres` links into the executable - so the title
bar/taskbar and Explorer agree by construction, with no new crate.

- Verified: the release exe **before** this work had `ExtractIconExW -> 0` icons;
  the new exe reports **1**, with the four quadrant centres exactly
  `#F85149 / #D29922 / #3FB950 / #8B949E`. `WM_GETICON` returns non-zero for both
  the big and small window icons. Debug and release both build and embed.
- Suite: core **21/21**, app **21/21** (+5 `icon_design`), e2e **18/18** (+2).
  Client-area counts `closed=2043 vent=5600 open=790 panel=0`; the tray's
  verdict-tinted icon and its `#f85149`/`#3fb950` assertions are unchanged.
- Assumption change: `.ico` is **BMP-flavour**, not PNG-in-ICO as first proposed,
  so the encoder stays pure `std` and `build.rs` needs no image crate (~285 KB).
- Side effect: the e2e harness now screenshots the **client area** (the title-bar
  icon's colours had polluted the "headline band" scan). Evidence:
  `experiments/EXP14/EXP14-icon-preview.png`, `EXP14-window-titlebar.png`,
  `EXP14-app-icon.ico`.

## Learnings
- Exe icon on GNU/MinGW, no crate: in `build.rs` write `$OUT_DIR/app.ico` +
  `1 ICON "app.ico"` `.rc`, run `windres -O coff -o out.o app.rc`, then
  `cargo:rustc-link-arg-bins=<out.o>`; works in debug and release. `windres` is
  at `%LOCALAPPDATA%\mingw64\bin\windres.exe`.
- Share one design between `build.rs` and the app with `#[path = "src/x.rs"]
  mod x;` (needs `std` + sibling `#[path]` modules only; `crate::theme` resolves).
- A BMP-flavour ICO (uncompressed 32bpp DIB + zero AND mask) is ~40 lines of
  pure `std` - no image crate.
- Set the window icon with `WM_SETICON` (ICON_BIG + ICON_SMALL); read it back
  with `WM_GETICON`. For the embedded icon, `ExtractIconExW` +
  `Icon.FromHandle(..).ToBitmap()` gives per-pixel proof.
- E2E screenshots of the window rect include the title bar; crop to the client
  area (`GetClientRect` + `ClientToScreen`) before colour-scanning the widget.
- `ld: .rsrc merge failure: multiple non-default manifests` is pre-existing
  (gpui_ce_windows vs MinGW's default manifest), not from the icon object.
- E2E flake: a physical cursor resting over the window raises the chart tooltip
  and fails `panel == 0`; park the cursor off-window before running.
